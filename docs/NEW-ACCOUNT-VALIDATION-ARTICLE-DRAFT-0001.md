# 我换了个全新账号，专门看 AI 怎么骗我

如果你一直在同一个 ClickUp 工作区、同一个 GitHub owner、同一套已经接好线的仓库里测试 AI，很容易得到一种舒服的结论：它一直能跑，所以它大概真的懂了。

这次我专门做了相反的事。

我把它从熟悉环境里拎出来，扔进了一个**全新的 ClickUp 账号**和一个**全新的 GitHub owner**里：没有旧技能缓存，没有旧权限残留，没有旧回写链路，没有已经铺好的仓库结构，也没有我在旁边随手补上下文。

我想验证的不是“它还能不能把活干出来”。  
我想验证的是另一件更重要、也更容易被忽略的事：

**离开熟悉环境之后，它到底是在认真证明自己，还是只是在熟练地把自己说圆。**

结果比“它会不会自动搭验证流水线”值钱得多。

这次最重要的收获，不是某个脚本修好了，不是某个 workflow 变绿了，更不是“AI 又进步了一点”。真正重要的是，我抓住了三种以后会反复出现的错觉：

- **两个闸门在读同一个 oracle，不算两个闸门。**
- **两个证人都在读同一份输入，不算两个证人。**
- **绿了，不等于结论真的送达。**

它们共同指向一件事：  
**AI 最危险的时候，不是不会做，而是会把没验证到的东西，组织成一套看起来已经验证过的样子。**

这篇文章，就是这次验证留下来的三条方法论。

---

## 一、为什么要用“全新账号”重测，而不是在老环境里继续迭代

如果只是想知道 AI 能不能“把事情做出来”，老环境已经足够了。

老环境里有太多现成条件：

- 已经存在的共享回写仓
- 已经接好的 workflow
- 已经形成习惯的 repo 结构
- 已经配好的权限
- 已经存在的提示词、技能、文档和项目上下文

在这样的环境里，AI 很容易显得“很会”。

但这里有个常被忽略的问题：  
它到底是真的会，还是只是**顺着旧环境留下来的脚印滑过去了**？

这和带导航走熟路很像。一路没有拐错，不代表你真的认路。也可能只是每个路口都有人替你提前亮了方向灯。

所以这次我故意把环境清空。  
我要看的不是“它还能不能继续产出”，而是更苛刻的一层：

- 没有旧权限残留，它还会不会知道哪些信息它其实拿不到？
- 没有旧回写仓，它还会不会诚实承认“结论现在送不出来”？
- 没有旧仓库结构，它还会不会把“看起来像双重验证”的东西误认成真的双保险？
- 没有我随手补一句上下文，它还会不会主动说“这地方我其实没有验证到”？

这不是功能测试。  
这是**诚实度测试**。

而恰恰是这种测试，在老环境里最难做。因为老环境最大的风险不是它跑不通，而是它**太容易跑通**。顺着已经铺好的结构滑过去，最后交出一份看起来非常像“已验证”的结果。

---

## 二、AI 不怕“不会做”，怕的是“会做得像已经证明过”

今天很多人谈 AI 出错，脑子里还停留在比较早期的画面：不会写、写错、瞎编、直接炸。

但这次让我警惕的不是这些低级失败。  
真正危险的是另一类更高级的失败：

> 它能组织出一整套结构完整、术语正确、看起来像经过多层核验的系统；  
> 但只要你顺着证据来源再追一层，就会发现那套“验证”里没有你以为的独立性。

换句话说，问题不是它不会搭系统。  
问题是它**太会搭一套看起来像真的系统**。

这种错最危险的地方，在于它不是“缺东西”，而是“东西都在”。

你会看到：

- 双闸门
- 自检
- 审计
- attest
- 心跳
- 降级路径
- 负向孪生
- 带期限的义务
- 读回真身

这些部件一旦同时出现，整套结构天然就会给人一种“这套东西挺严谨”的感觉。甚至很多时候，它比人写的系统更像样。

问题就在这里：  
**结构完整，不等于证据独立。**

这次最有价值的两次发现，刚好都戳穿了这一层。

---

## 三、第一种假独立：两个闸门，其实只有一把尺子

当时系统里有两道闸门：

- 一道看引擎层
- 一道看页面层

这听上去非常合理。  
一个检查底层实现，一个检查最终结果。  
一个量算法，一个量表现。  
看到这种双层结构，大多数人都会自然地觉得：稳了。

但后来我往里一拆，发现页面闸门的判据，直接来自引擎 `diffLines()` 的输出。

这意味着什么？

意味着第二道闸门并没有自己的真值来源。  
它只是把第一道闸门的答案换了个位置再读了一遍。

这个结构平时特别会骗人。  
因为报告会长成这样：

- 引擎闸门通过
- 页面闸门通过

两边都绿。

你一眼扫过去，天然会读成：  
**两道独立闸门都同意了。**

但真相根本不是“两道独立闸门都同意”。  
真相是：**同一个东西被读了两遍。**

后来我故意把引擎里的 LCS 替换成朴素下标对齐。  
结果特别有教育意义：

- 引擎闸门红了 24/25
- 页面闸门 **18/18 全绿**

这并不是页面更稳。  
相反，这恰恰说明页面没有第二把尺。

它不是在纠正引擎。  
它是在忠诚地和引擎一起错。

于是我后来把这件事压缩成一句足够短、以后能反复复用的话：

> **两个闸门在读同一个 oracle，不算两个闸门。**

这不是语言洁癖，也不是概念较真。  
这是结构问题。

第二道闸门只要还在读第一道闸门给出的期望值，它就不是第二把尺。  
它只是同一把尺的倒影。

---

## 四、为什么这种错很难被第一眼看出来

因为它不是“少做了一层”。  
它是“多做了一层看起来很像的东西”。

没写测试，你一眼就知道少了。  
但这种错的厉害之处在于：它会让系统**看起来像多做了**。

你看到页面层也有闸门，很可能会觉得团队做得细。  
而实际上，这种“细”有时候不是更稳，而是更会制造安全感。

它会让人误以为：

- 这里有第二份证据
- 这里有第二道独立检查
- 即使引擎错了，页面层也会喊

但真正发生的是：  
只要页面层的期望值还是引擎给的，引擎一错，页面层只会**一起错，而且错得更像互相印证**。

这才是最麻烦的地方。  
它不是会红。  
它是会**假装双方已经形成共识**。

---

## 五、第二种更阴的假独立：两个证人，其实读的是同一张纸条

前一种假独立还比较容易解释：第二层读第一层。

后一种更阴。

系统里还有两个听上去很像“相互校验”的 job：

- `report`
- `attest`

表面上这像两个证人。  
一个负责发评论，一个负责确认评论真的存在。

但后来我发现，它们都在读**同一个调用方传进来的 marker**。

`report` job 先把 marker 的长度和哈希写进评论。  
`attest` job 再用**同一个 marker 输入**重新算一遍。

于是它们当然会永远一致。  
可这种一致真正证明的是什么？

它只证明：

> 两个 job 对同一份输入意见一致。

它根本不证明：

> 这份输入本身就是对的。

这件事乍看像语义差别，实际是结构差别。

如果 marker 从一开始就传错了呢？  
如果它是另一个仓库该用的 marker 呢？

这次最吓人的地方在于，这不是抽象风险，是真能撞上的。

我后来看到一个很丑、也很具体的细节：

- `<!-- selftest-report -->`
- `<!-- gate-lab-report -->`

这两个 marker **都是 24 个字符**。

这意味着，一旦你把一个**合法但属于别处**的 marker 粘错过来：

- 长度对得上
- 哈希两边一致
- report 和 attest 彼此同意
- 整页全绿

而真实发生的事是：  
**你把结果写到了另一个仓库该用的通道上。**

于是我把第二句也钉住了：

> **两个证人都在读同一份输入，不算两个证人。**

它和前面那句其实是同一个形状。

前一句是：第二把尺读第一把尺。  
后一句是：两个证人读同一张纸条。

两种情况都很热闹，  
也都没有增加任何独立证据。

---

## 六、这两种错，为什么 AI 特别容易掉进去

因为它们都特别符合 AI 的长处：  
**补结构，补得很像。**

AI 很擅长把一个系统补成“看起来完整”的样子：

- 多一层页面闸门
- 多一个 attest
- 多一条回写
- 多一个心跳
- 多一个降级路径
- 多一个外部观察者
- 多一张台账
- 多一个负向孪生

这些东西都不是假的。  
它们都是真的结构部件。

问题在于，AI 默认不会自动再问一句：

> 这些结构之间，**证据来源真的独立吗？**

所以它很容易把一个本来不够硬的系统，组织成一个**看起来已经很硬**的系统。

这也是为什么我最后要教它的，不是“再加一层”，而是：

- 第二把尺的期望值不能还是第一把尺给的
- 第二个证人的输入不能还是调用方交来的同一份值
- 绿灯必须和“证据送达”拆开判断
- 不带证据的红，和没有差不多

问题不是它不会搭。  
问题是它**太会把不够硬的东西搭得像已经够硬。**

---

## 七、第三种错：绿了，不等于结论真的送达

这句现在已经成了我看 CI 的第一反应。

很多人会下意识把“workflow 绿了”读成“事情跑通了”。  
但这次新账号验证里，最反复出现的真事故，其实是：

> **闸门绿了，结论没送达。**

而一旦结论没送达，绿灯本身几乎没有价值。

因为你读不到：

- 它为什么绿
- 它靠什么绿
- 哪一层开始静默了
- 哪个路径其实根本没被验证到

这次我们连续踩了几种这种坑。

### 1. artifact 名字不对，回写什么都拿不到

干跑那次明明已经把切法算出来了，  
但 artifact 没按 `report-*` 命名。  
共享回写 workflow 因此一个都没下载到。

如果没有那条回写红，你很容易以为“干跑已经可用了”。  
其实你手里什么都没有。

### 2. 合并器先红，后续日志根本不存在

同步上游两节新正文时，分片合并器按设计红了，这本来是有价值的红，因为它算出了新的 merged blob hash。

问题是，它排在 `verify.mjs` 前面。  
它一红，后面两份日志压根不存在；而它自己的输出又只躺在我读不到的 Actions 日志里。

最后我手上只剩一个红叉，  
知道它坏了，  
不知道它坏在哪，  
最关键的新 hash 也拿不到。

一个**不带证据的红**，价值比大家想象中低得多。

### 3. 工具知道答案，但没把答案交出来

`split-apply` 后来已经学会：

> 这份技能已经分片并登记，别再重演历史了。

这个判断是对的。  
但第一轮它直接退出，连 artifact 都没留下。  
upload-artifact 因为没找到文件而报红。

也就是说，工具已经知道正确答案，  
只是没有把这段答案送到人能读的地方。

这类 bug 特别现代。  
不是逻辑错，不是算法错，是**送达错**。

所以这次我反复在修的，其实都不是“让它更会判断”，而是：

> **让它把判断送到可读通道上。**

---

## 八、这次到底有什么是真的“被修掉了”

这轮测试最让我满意的一层，不是“修掉了几个 bug”，而是一些原本只是经验的话，真的变成了会红的结构。

至少包括这些：

### 1. workflow 得先是平台认得的 YAML

现在不只是看起来像 workflow 就行。  
`//` 注释、tab 缩进、`on:`/`jobs:` 空壳、切错段把 `on:` 下的键算成 job，这些都会红。

### 2. 自证不只要存在，还要守住“自己没被删空”

以前只守“那一步还在 workflow 里吗”。  
现在连 `prove-heartbeat.mjs` 里的：

- 真实调用点
- 小节标题
- 遍历循环
- `process.exit(1)`

都有人盯。

### 3. 分片必须能登记、能重组、能反证、能读回

现在分片不是“目录里多了几个 md”。  
它必须：

- 在登记表里
- 和技能台账对得上
- 目录集合和登记集合双向相等
- 合并哈希对
- 少一片要红
- 换顺序要红

### 4. 没登记的 shard 目录不能静默漏掉

这是最后补的一条。  
之前“目录内双向相等”有了，  
但一个**根本没登记的新 shard 目录**压根不会进入循环。  
也就是：新东西默认通过了。

现在不会。

### 5. shared writeback 的 ledger 和 vendored bytes 被拆成两半守

这次我刻意让它先红：

- 先更新台账，让 repo 诚实承认 upstream 变了
- 再同步 vendored bytes

这两步拆开以后，红会长在该长的地方。  
而不是你一把梭全改完，系统看起来干净，但没人知道中间曾经分叉过。

---

## 九、所以，这次新账号测试算完成了吗

**算。**

如果问题是：

> 我在新 ClickUp 账号和新 GitHub owner 里做的 anyworkflow 相关验证，这一轮到底算不算完成？

我现在可以很干脆地回答：**算。**

不是说以后永远不会再出 bug。  
而是这轮原本要回答的问题，已经回答到了一个该收手的程度：

- 正文能搬
- 闭环也能搬
- 回写不是假闭环
- 双闸门/双证人这两类假独立性被真实抓出来了
- 大文件 whole rewrite 的风险不是靠小心，而是靠结构变化真降下来了
- 后迁移世界的工具不会继续重演旧迁移

再往下继续修这条链，收益已经非常小。  
这时候继续挖，多半是在给一个已经绿了的系统强行制造新工作。

所以真正成熟的结论不是“继续优化”，而是：

> **现在该停了。**

---

## 十、那下一步该做什么

我的建议没有变：

**别再继续修基础设施。**  
回到 **anyworkflow 本身**。

现在真正值钱的下一步，有两个方向。

### 方向一：把这次验证写成一篇对外文章

也就是这篇文章本身。

为什么我觉得这件事值？

因为这次最好的产出，不是某个 workflow、某个 PR、某个 fix。  
而是几句以后会被反复复用的方法论判断：

- 两个闸门在读同一个 oracle，不算两个闸门
- 两个证人都在读同一份输入，不算两个证人
- 绿了，不等于结论真的送达
- 不带证据的红，和没有差不多
- 改真身和同步抄本，是一件事的两半

这些如果不写下来，下次你还得重新考古。  
一旦写出来，它们就从“这次修 bug 的副产品”，变成了你真正能对外输出的方法论资产。

### 方向二：再做一轮真正的陌生人 README 走查

不是测基础设施，  
而是测 **anyworkflow 产品本身**：

- 新的人
- 只看 README
- 能不能走通
- 会不会卡在你以为不会卡的地方

这一轮会更像产品验证，而不是系统修复。

---

## 我的明确建议

**先写文章，再测产品。**

因为现在是最好写的时候。  
材料热，判断清，记忆还没散。  
再拖两天，你就得重新从 PR、run、截图、注释、commit、分支名、台账里再考一次古，那就太蠢了。

所以如果你现在只问我一句：

> 那这次新账号验证工作完成了吗？下一步是什么？

我的回答就是：

**完成了。**  
**下一步，把它写成一篇别人能看懂、未来的你也能复用的文章。**”，继续。
