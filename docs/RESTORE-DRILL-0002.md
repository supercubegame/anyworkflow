## 这次仍然证明不了什么

**一、父技能做不到字节精确，而这不是恢复的缺陷。** 写通道会把畸形的强调标记重新序列化,备份里那段本来就是富文本留下的痕迹（`<strong>` 与 `**` 混用），平台读不成合法结构就按自己的规则重写。**这条现象备份仓自己的 `GATE-SHAPES` 里早就写着，只是此前只在备份方向被观测过。**

**二、把 8 个星号收回 4 个之后，长度回到 26121 而 blob 仍然不同。** 长度相同而 blob 不同 = **至少还有一处同宽差异**。定位它需要两份字节在同一个地方，而沙箱没有外网、手打 26KB 中文是 0/2 的通道。**我能证明「至少还差一处」，指不出它在哪。**

**三、Skills Hub 界面列表读不到。** 那边没有能渲染 UI 的通道。斜杠选择器里出现过，**但那不是 Hub 列表，两个观察面不许合并。**

**四、「界面显示名」在 CLI 上不是一个字段。** 它是 `name` 的大写 ASCII slug,派生量，信息量为零。

**五、二次保存会不会继续翻倍，本次没验。** 这决定那条归一化是一次性还是每次保存都增长，而如果是增长，**顶到 12000 上限的会是余量只剩 1209 的 `mutation-check-assertions`，不是父技能。**

## 这次新发现的风险

**风险一：备份台账里父技能的 `name` 是错的，错了整整二十天。** 登记成 `AGENT 自验证流水线`，而真身一直是 `Agent 自验证流水线`。写通道拒绝全大写（`SKILL_NAME_ALL_UPPERCASE`）才暴露了它。

- 它为什么危险：那条记录挂着 `name_is_reconstructed: false`,**一个声称已核对过的字段**。
- 当前有断言在守吗：**没有**。唯一相邻的字段是 `clickup_display_name`，而它是 `name` 的大写 slug,`Agent` 与 `AGENT` slug 出来都是 `AGENT`。**一个派生量证不了它源头的大小写。**
- 后续：登记表那一侧要改。而它住在一份 22KB 密集中文里，只能整文件覆盖,**基线证不成就不推**，所以这一步归人或归一条 CI 补丁器。

<p><br/></p>

**风险二：我差点执行一个会主动弄坏正确断言的修法。** 那一侧建议把分片台账的 `merged_blob_sha1` 改成回读到的值。**理由听起来很对，动作是反的** —— 那个字段描述的是备份仓自己的字节，改了之后合并器下一次必然红。收窄成一句：**一个登记值该不该改，判据是「它描述的是哪一侧的字节」，不是「哪一侧此刻更新」。**

<p><br/></p>

**风险三：`skill` 任何命令行里混进 `--help` 就恒等于 0。** 不存在的子命令本身退出码是 1（报 `UNKNOWN_COMMAND`），`skill check` 在真有错的目录上也是 1。**所以口子很窄但真实**：谁在 CI 里写成 `skill check --help`，那道闸门永远绿。当前没有任何断言在守,而这仓此刻也没有任何 CI 步骤在跑 `skill`，**给一个当前没有输入的检查器加断言得先想清楚它守的是谁**，所以先登记不先建。
