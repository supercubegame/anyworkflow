# 完整工作流程示意图（文字版）

## 标题
Agent 自验证流水线：完整工作流程示意图

## 这张图要表达的一句话
这套系统不是“AI 写代码”那么简单。它是一个闭环：Agent 先给自己设闸门，只读机器能读懂的证据；过不了就自我修复；最后把结果交给外部观察者持续巡检。每一步都有可验证的输出与可追溯的记录，确保“能被证明”，而不仅仅是“看起来对”。

## 六个阶段

### 1. 用户提出需求
输入形态：新项目、新功能、新仓库、新实验。

这一层真正重要的不是需求有多完整，而是：
- 有没有明确目标与范围
- 有没有“跑起来了”的判据
- 有没有会影响后面验证方式的项目类型信息

### 2. 技能被匹配并加载
如果这是一个代码 / 游戏 / App / 仓库自动开发类请求，应该先匹配到「Agent 自验证流水线」。

这一层守的不是“内容会不会做对”，而是：
- 该被加载的时候会不会真的被加载
- 冷启动会话里，方法论能不能先于实现进入上下文

这是当前仍然最像沉默通道的一层：**技能可能安静地不被加载，而对话看起来完全正常。**

### 3. 先搭验证闸门，再写功能
这是整套方法的硬顺序。

先做一条唯一入口命令，让项目返回：
- exit 0：通过
- exit 1：失败

并把真实输出写出来。常见形态是：
- 快闸门：零依赖、几十秒出结果、纯核心或静态不变量
- 慢闸门：真页面 / 真窗口 / 真外部系统

这一层的核心原则是：**先有尺子，再做东西。** 不然第一次跑起来时，产品、夹具、阈值、回写会一起红，根本分不出是谁弄坏的。

### 4. CI 自动运行并回写可读结论
CI 跑闸门不够，结论必须被 AI 读到。

所以至少要有：
- PR 评论路径
- commit 评论路径
- artifacts
- 一条 attest 回头确认评论真的出现

这层守的是那句最值钱的话：**送不出结论的闸门，等于没跑。**

### 5. AI 读取证据并自修
当闸门红时，正确顺序不是“改产品直到不红”，而是：
1. 先查尺子是不是在说谎
2. 再查夹具是不是没满足前提
3. 最后才改产品

mutation checks 的作用也在这一层：
- 把要守的东西故意改坏一次
- 看断言会不会真的红

这一步防的是另一类假绿：**断言存在，但不承重。**

### 6. PR 绿后合并，外部观察者继续巡检
PR 绿并不是终点。主干上的定时、心跳、共享 workflow、跨仓台账、备份抄本，仍然可能继续漂移。

所以需要仓外观察者：
- Quinn：09:20，横向巡检，盯跨仓与外部真值
- Devon：10:20，纵向兜底，盯备份自身是否变旧、变假、或复读 Quinn
- heartbeat.json：带时间戳的正向痕迹

## 右侧那列“沉默通道”到底在提醒什么

### 回写失败
闸门可能是绿的，但评论没送出来。没有评论，AI 就等于失明。

### cron 静默停用
工作流文件一个字都不变，但定时任务已经死了。只有带时间戳的外部痕迹能证明它还活着。

### 台账自洽但不为真
本仓里的 ledger 可以彼此对得上，但别的仓库早就变了。

### 抄本不是真身
导出的 skills / prompts / agent JSON 只说明“上次有人这么抄过”，不说明现在真身还是不是这样。

### 写入通道整文件替换
文件一旦长到某个尺寸，一次“只想改一行”的写回会顺手抹掉别的东西，而顶层键可能还一个不少。

## 核心原则（图底部五个词）
- 先闸门后功能
- 读证据不读感觉
- 一条规矩被违反两次就变成断言
- 自洽不等于为真
- 观察者不能是被观察的那个

## 这张图不打算替代什么
它不替代：
- 事故台账
- 恢复步骤
- 盲区清单
- 具体某个仓库的实现细节

它只负责把整条链路讲清楚：**从需求到闸门，到回写，再到观察者，信息是怎么闭环的。**
