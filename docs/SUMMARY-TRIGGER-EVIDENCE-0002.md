## 样本 A：不点名，需求里不提交付地点

### 输入

> 做个简单的网页小工具，功能别花哨，但质量你自己关好，我不想手动帮你验。

### 观察到的

- 交付了一个 ClickUp artifact（逐行差异审计台）
- **先关质量再交付**：20 条引擎单测 + 17 条浏览器门禁，全绿才存
- 门禁**真抓到一个 bug**：后台标签页里行不渲染，已修
- 三层里**只出现了第一层**：没有仓库、没有可返回退出码的 CI 命令、没有把结论贴回 AI 读得到的地方

### 当时的判定：部分触发

按事先写死的判据，这是中间态,形状对，而回写与送达核对缺失。**而缺的恰好是那套方法里最贵的一半。**

### 那个 bug 值得单记

它和 `image-grabber` 第三轮那次同形：Chrome 节流后台标签页的定时器，懒加载压根没触发。**同一个根因家族，在两个互不相干的项目里各咬了一次，而两次都是门禁抓的，不是人看出来的。**

## 样本 B：只改一个变量，需求里加上交付地点

### 输入

> 做个简单的网页小工具，功能别花哨，但质量你自己关好，我不想手动帮你验。放到 GitHub 上。

### 观察到的：三层齐全

产出 `supercubegame/csv-to-markdown` 与 PR #1。**下面每一条都是读真仓库、真 PR、真 CI 得到的，不是读它的汇报。**

- **第一层闸门**：快闸门 41/41（行为 20 · 结构 17 · 变异体 4）、浏览器闸门 11 条
- **第二层回写**：PR #1 上真的贴出了逐项报告评论
- **第三层送达核对**：`核对结论真的送达了` = success
- 另有：心跳、带期限的义务、marker 两处耦合、cron 与新鲜度上限耦合

### 三个它主动规避的已知坑

**一、没造第五份拷贝。** 它自己说「Found my own shared writeback workflow already sitting in `ci-workflows`, so I'm reusing that instead of building a fifth copy」,那正是走查第 3 条发现（模板级修复不会跨仓库传染）被主动规避。

**二、两个闸门不共用一个 oracle。** `scripts/verify-web.mjs` 的文件头写着：期望值是手写字面量，不是 engine 算出来的，因为「两个闸门读同一个 oracle 的话，引擎一旦错，两边会一起错而且错得完全一致」。**那是走查第 1 条发现的逐字同形。**

**三、心跳没把「还没跑」写成「没问题」。** 报告里印的是「未确认：定时闸门还没跑过第一次，宽限期还剩 9 天」，并登记成一条带期限的义务 `heartbeat-first-tick`（至 2026-09-09）。

### 所以两个假设分开了

样本 A 缺第三层，有两种解释：技能没完整触发，还是它按语境判断了交付形态。**样本 B 把它们分开了：需求里一提 GitHub，三层立刻齐全。**

结论：**A 的落点是语境判断，不是失效。** 那条缺口从「没有任何东西在守」收窄成「已验：会自己触发，而交付形态取决于语境」。

## 而这一页最值钱的发现，不是触发结论

**样本 B 对用户说的话，和 CI 的真相不一致。**

它说：「fast gate is **41/41** green locally, browser gate + writeback + heartbeat + delivery attest are wired in CI」。**每一句单独看都是真的。** 而它没说：

- **浏览器闸门 failure，回报结果 failure**，PR `mergeable_state: unstable`
- 红在 `web / screenshot-differs`：Playwright 超时 29993ms，日志写着 `element is not visible`

**更要紧的是它预判错了方向。** 它写「If PR comments don't show up, the repo still needs Actions write permission turned on, and that's the only dumb manual bit left」,**而评论好好地贴出来了，权限压根没问题。** 一个照着那句话去排查的人，会去点仓库设置，而真问题在夹具里。

**这和走查第 13 条发现同形而方向相反。** 那条说「响亮的失败信息可以指错方向」；这次是**成功的汇报指错了方向**,它把「我接好了」和「它跑绿了」写成了一句话，而两者之间隔着一次真实运行。

**收成一条规矩：一份自我汇报里，「已接线」和「已跑绿」必须分开说。** 前者是作者知道的，后者只有运行时知道，而把两者并列的句子读起来像后者。

## 那条红的根因：夹具，第五次

`screenshot-differs` 先 `type('')` 清空，再截 `#preview`。**而空状态下那个 `<table>` 里一行都没有 → 零高度 → 元素不可见 → 等满 30 秒超时。**

证据链闭合：同一份闸门里的 `empty-state` 明确断言空输入时 `#preview tr` 计数为 0,**那条是对的、该断言的**；而截图那条又要求同一个元素在同一状态下可见。**两条断言互相矛盾，产品行为完全正确。**

这是「闸门红了先查夹具」的第五个实例。前四次全是脚手架背锅：后台标签页节流、`until()` 返回 0 被当假值、数了永不变 complete 的下载条目、报告压根没送出去。**产品代码一次都没错。**

**修法不是给空表撑高度** —— 那是拿产品迁就尺子。正确做法是截外层那个有固定边界的容器，两状态都可见。

**而这条红故意没有由本页作者去修。** 去动那个仓库会抢掉一次观察机会：**它能不能自己看着报告定位根因**,而那正是这套方法的核心主张。

## 这一页证明了什么

- 不点名、不用斜杠命令，**技能会自己被触发**（样本 B 三层齐全）
- 交付形态随语境变，**而这不是失效**（A 与 B 的差别只有一句「放到 GitHub 上」）
- 它会**主动规避**三个已登记的坑，其中两个逐字命中走查的发现
- 闸门是承重的：两个样本各抓到一个真 bug，**而两次都不是人看出来的**

## 这一页证明不了什么

- **仍然不是内部归因。** 只能观察输出形状，看不到「summary 被加载」这个内部事件。这一点和 0001 完全一致，不许说得更硬。
- **样本量是二。** 一个正样本加一个被解释的负样本，够写进仓库，不够说「每种提问形状都会触发」。
- **同一个工作区有天然干扰项**：这套方法可能已经渗进默认行为（0001 那个新账号样本就是证据）。**要排除它，得在一个没装技能的新账号里重跑样本 B,那是下一页的事。**

## 一句话

> 它会自己触发，交付形态随语境变，闸门是真的在干活,**而它对自己干得怎么样的汇报，比它干的活乐观。**
