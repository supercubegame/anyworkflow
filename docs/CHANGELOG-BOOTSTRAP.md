# Bootstrap Changelog

这不是项目更新日志。它只记录 `anyworkflow` 这份离线备份仓**是怎么长起来的**，以及哪些里程碑已经具备了可读证据，哪些还没有。

---

## Phase 0: 空仓初始化
- 手动新建仓库 `supercubegame/anyworkflow`
- 第一个提交只种下 `README.md`，把空仓变成有默认分支的仓库

**当前证据强度**：弱。只有 commit，没有 PR 交付链。

---

## Phase 1: 最小诚实闸门
落下这些最小结构：
- `AGENTS.md`
- `CLAUDE.md`
- `manifest.json`
- `verify.py`
- `.github/workflows/verify.yml`

这一步的目标不是“备份完整”，是先保证**这份备份仓自己不会安静地说谎**：
- 规则文件必须同步
- 恢复文档必须存在
- 盲区清单必须存在
- `not_backed_up` 不许是空数组
- `manifest` 顶层键不能缺

**当前证据强度**：中。结构齐了，但最开始那几步是直写 `main`，没有一条可读的 green PR 证据链。

## Phase 6: 这仓自己终于有了回写与送达核对

在这一步之前，**这份仓库示范的是一套三层方法，而它自己只有第一层。**

`.github/workflows/verify.yml` 一共 313 字节：checkout + 跑闸门。没有回写、没有 artifact、没有送达核对。而这不是“还没做”，是一件已经被实测确认的事：**PR #10 的闸门是 success，那条 PR 上评论 0 条。**

同期对照更难看：同一个 owner 下的 `crossyroad`（一个网页版过马路小游戏）的 verify.yml 是 7.2KB，双闸门 + pipefail + artifact + 心跳 + 走共享 workflow 回写。**一个小游戏的闭环比方法本仓完整。**

这一步补的：
- `scripts/compose-report.mjs`：把逐项结果合成评论（共享 workflow 的调用方约定要求 Node 入口）
- `scripts/attest_delivery.py`：回头去 API 上确认**这一次**那条评论真的存在，带一批合成样本的离线自证（样本数由那张表算，不手写）
- `verify.py`：逐项结果落成 `artifacts/verify-report.json`；新增两条断言守这次接线自己造出来的两组耦合参数
- `.github/workflows/verify.yml`：闸门（pipefail + artifact）-> 回写（`ci-workflows/report.yml@main`）-> attest（`always()`，红的那次也要证明送达）

**这一步没有做的一半，明写在这里：**
1. ~~真抄本仍然在闸门视野之外~~ —— **Phase 7 补上了**。
2. `manifest.invariants` 仍然是声明，没有任何东西核对它和实际检查集合相等。
3. 没有定时、没有心跳：「cron 静默停用」那一类在这仓还不适用（目前没有 cron），但一旦加了定时就必须同时加心跳。
4. `LIVE-READBACK-LEDGER.md` 的读回时间仍然是散文，没有期限断言。
5. `docs/INDEX.md` 自称 full index，实际还漏着几份文档。

**第一轮实测（PR #14，run 32905110223）**：三个 job 全绿，attest 也绿 —— 评论真的送出去了，带 composer 哨兵、本次短 SHA、本次 run id。两条边界要写清楚：

- **只走了 commit 评论那条通道**（回写跑的时候 PR 还没开）。
- **attest 当时还没在 live CI 里红过。**

而那两条边界后来都补上了：PR 通道在 run 32907123136 走过；attest 在 run 32911142277 真红了一次。详见 `VERIFY-EVIDENCE-0003`。

**顺带抓到一件不在计划里的事：推上去的字节可能不等于本地真源。** 逐个文件读回核对 blob 哈希时发现多处中文被换成了形近字，而且**字节长度不变** —— 于是体积与关键字类检查全部看不见。

**而根因后来彻底定位了，我改过一次口：不是存储通道，是我自己。** 我往文件里写中文时会敲成形近字，手写 Unicode 转义时会敲错码位（差一位）。最早那个结论指控了一条我验不了的通道，那是错的。

**修法不变，而且现在有两条断言在守：**承重文件的逐字节身份（blob 哈希），以及一条形近错字黑名单的负向扫描。

**当前证据强度**：三分之二。“评论送得出去”有实测（两条通道各一次）；“闸门红的那次也送得出去”有实测（run 32908614769）；**attest 自己也真红过一次**。

## Phase 7: 真抄本终于进了闸门视野

Phase 6 明写的那笔欠账还了。闸门 10 -> 16 条。

**先改口一件事：**我曾说过「blob 哈希已经盖住 agents/ 和 vendor/」。**那句话是错的。** `REGISTERED_DIRS` 当时只有 `docs` / `scripts`，登记表里一条 `agents/` 或 `vendor/` 的条目都没有 —— 三份真抄本整个删掉都不会红。现在才真的盖住了。

备份类那四条全齐（详见 `MINIMAL-GATE.md`）：清单双向、逐字节身份、正文锚点、恢复充分性、新鲜度。

**另外三条都不在计划里，都是做这一步时撞出来的：**

**跨抄本一致性 —— 而它上线就抳到了一个真问题。** 一个观察者的 prompt 里写着另一个观察者的定时应当是某个值，而那个值已经不是真实的 cron 了。**两份抄本各自都是忠实的读回，而它们互相矛盾 —— 这种形状没有任何单份断言看得见。** 修不在本仓，所以登记成带期限的义务，完成判据读两份真文件而不读我的报告。

**形近错字黑名单。** 那个反复发生的字节漂移，根因彻底定位了：**在我自己，不在存储通道**。黑名单用码位构造并带自证，而它上线后当场抓住我两次、在 CI 里又抳到两份旧文档里的十处遗留。而写这一节的时候它又抓住我两次。**次数不写在这里** —— 那是散文里注定漂的那种手写数字，真值记在 `manifest._tested_limits` 里。

**检查总数等号 + 交叉核对 MINIMAL-GATE 里那个数。** 那份文档写着「守哪七件事」而闸门早就不是七条 —— 散文里的数字注定漂。真值在同一个仓里，所以这条交叉核对做得成。

变异体十三个，全部就地实测判红，包括「删掉新鲜度上限」那个 —— 它原本是 `TypeError` 崩溃，而**崩溃不是红**：报告压根不落盘，composer 只能送一条降级评论。

**两笔新登记的「测不出来的」：**黑名单对新错字默认泄漏（实测两个漏网例子）；以及变异体不能拷到别处跑，`ROOT` 从 `__file__` 推，拷过去会崩而**崩溃看起来像变异体活下来了**。

**当前证据强度**：强。四条断言在 CI 里对着真文件全部通过（3 份抄本、十六条锚点、十二个必需小节）。**但它们一条都不证明抄本等于真身** —— 那件事只能从仓外读回，而新鲜度那条守的就是「有人 30 天内真的去读过一次」。

## 当前仍然欠的证据
1. **第一条完整的 green PR 证据链**
   到目前为止，大部分内容是直接写在 `main` 上长出来的。结构是真的、文档是真的，但交付链证据弱。
2. **真抄本和真身此刻是不是一致**
   Phase 7 那四条只能证明抄本没被改过字、没被抽空、读回不超 30 天。**它们一条都不证明抄本等于真身**，那件事只能从仓外读回。
3. **summary 自动触发归因**
   行为证据已经有了（`SUMMARY-TRIGGER-EVIDENCE-0001`，正负样本各一个），内部归因仍然不在本仓能证明的范围里。

## 为什么这份文件存在
因为以后回头看，最容易发生的错觉是：

> 仓库里这些文件一直都在。

不对。它们是分阶段长出来的，而且每一层解决的是不同的坏法。

这份 changelog 守的是“来路”，不是“现状”。
