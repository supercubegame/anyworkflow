# 从零跑通：ClickUp Skills（Agent 自验证流水线）+ GitHub MCP

## 这份文档是给谁的
给**第一次接触这套系统的人**。默认你不知道它之前怎么搭过，也不知道哪些步骤只是抄文件、哪些步骤必须去读真身、哪些地方只能靠手动截图或 live 证据。

这份文档的目标不是解释理念，而是让你：

> 从空白开始，最后真的让它跑起来，而且知道自己哪些地方还没证明。

如果你只想快速理解结构，先看：
- `README.md`
- `docs/FULL-WORKFLOW.md`
- `docs/OFFLINE-BACKUP-SCHEME.md`

---

## 先说一句最重要的
这套系统不是“导入一堆文件就结束”。

它有三层东西：
1. **文件抄本**：规则、workflow、prompt、台账
2. **live 配置**：ClickUp Skills、Super Agents、GitHub Actions 权限、Secrets
3. **证据链**：green PR、negative proof、heartbeat、readback 时间账本

前两层不等于第三层。你把文件都抄回去，不代表系统真的活着。

---

## Phase 0：你需要准备什么

### 账号与权限
你至少需要：
- 一个 ClickUp 工作区
- 一个 GitHub 账号
- GitHub 仓库创建权限
- Actions 写权限（回写评论必须靠它）
- 能在 ClickUp 里创建 / 编辑 Super Agent 的权限
- 一个可用的 GitHub MCP 连接

### 仓库
至少需要这些 GitHub 仓库角色：
- 一个**共享回写仓**（例如 `ci-workflows`）
- 一个或多个**被验证的项目仓**
- 一个**离线备份仓**（例如 `anyworkflow`）

### 你要接受的现实
有些东西现在就是不能只靠仓内文件证明：
- skill summary 自动触发
- ClickUp UI-only 字段
- agent 工具在界面上显示成什么名字
- prompt 里的散文在仓外改动后是否仍然为真

这些以后都要写进 blind spots，而不是假装它们已经被覆盖。

## Phase 1：先搭共享回写，不要先搭产品

### 为什么先做这个
因为如果 CI 绿了但评论送不出来，Agent 还是瞎的。你会得到一条最阴的坏法：

> 闸门跑了，但没有任何人读得到结论。

### 共享回写仓至少要有的东西
- 可复用 workflow：`report.yml`
- 自检 workflow：证明它自己能送达 PR 评论 / commit 评论
- 两条路径都要通：PR 评论与 commit 评论
- 送达后回头确认 marker 存在
- 降级报告必须自己说明自己是降级，并让 job 红

### 这一层的手动设置
- GitHub Actions 权限要开写评论
- 如果要跨仓访问，需要对应 token / secret
- 如果你用的是组织仓，要确认创建时间和授权范围没卡住目标仓

---

## Phase 2：再搭一个最小项目验证仓

不要一上来就拿最复杂的仓库做实验。先拿一个最小项目仓，证明闭环通：
- 有一条唯一入口命令
- CI 能跑
- 报告能回写
- attestation 能确认评论真的存在

### 你该优先选什么项目类型
优先选**网页 / 静态站 / 单页游戏**这种完全自动档。原因：
- 好起浏览器
- exit code 明确
- 容易做快闸门 + 慢闸门分层
- 更容易在 PR 评论里给出读得懂的证据

---

## Phase 3：第一次新对话怎么发

### 目标
不要把整套方法论先讲给模型听。先给它一个足够明确、但不替它设计方法的任务，看它会不会自己进入“先闸门后功能”的工作方式。

### 示例提示词 1：网页小游戏
> 做个 2D 小游戏，自己把质量关好，我不想手动帮你验。

### 示例提示词 2：网页工具
> 做个简单网页工具，功能别花哨，但要自己把交付质量关好。

### 示例提示词 3：浏览器扩展
> 做个 Chrome 扩展原型，先把验证和回写链条搭好，再做功能。

### 你不该在第一句就塞进去的话
先别主动喂这些：
- “先搭验证闸门”
- “返回退出码”
- “PR 评论回写”
- “attest”

因为一旦你把这些原句全喂进去，之后你就分不出：
- 是 skill summary 自动触发了
- 还是模型只是顺着你的原句复读出了正确结构

---

## Phase 4：模型第一次正确响应时，你要看什么

不是看“它会不会写代码”，而是看它会不会先做这几件：
- 先判断项目类型
- 先定义“跑起来”的判据
- 先搭 gate，再写功能
- 主动把回写路径说出来
- 把需要你手动做的设置提前说清楚

### 如果它上来先写功能
别接着让它写。打断，回到“先闸门后功能”。

### 如果它问你项目类型和判据
这通常是好信号。说明它没在编一个假确定的路径。

## Phase 6：怎么判断它真的跑通了
至少要有这几类证据：

### 1. 绿灯证据
- 有一条 green PR
- CI 的主要 job 绿了
- 评论真的送达了

### 2. 负向证明
- 至少有一次 deliberate red -> green
- 不是语法错，而是有意义的坏输入
- 红在该红的地方，不是整坨脚本陪葬

### 3. 正向痕迹
如果有定时 / 心跳：
- heartbeat 文件真的写过时间戳
- 手动写入链路和真正 schedule 是分开的
- 一次手动盖戳不会污染 freshness 字段

### 4. 真抄本账本
- prompt / workflow 的最后一次 live readback 时间被记下来

---

## Phase 7：再把这套东西备份下来
当它跑通之后，才开始做离线备份仓。

离线备份仓至少要有：
- 规则文件
- 恢复步骤
- 盲区清单
- 事故台账
- 依赖台账
- 观察者分工
- 共享 workflow 归档拷贝
- 承重 agent prompt 抄本
- live readback 账本
- 最小诚实闸门
- green 证据 + red -> green 证据

否则你只是把文件存起来，不是把“这套系统为什么能信、为什么还不能全信”存起来。

## 常见失败形状

### 1. 闸门是绿的，但没人读得到结论
根因通常在回写链路。

### 2. 心跳存在，但不能证明 schedule 真跑过
根因通常是把 manual 和 scheduled 字段混了。

### 3. 抄本和台账都对，但外部世界已经变了
根因通常是真值住在别的 repo 或 ClickUp UI 里。

### 4. 大文件整文件替换开始咬人
表现：数组被静默清空、转义被吞、文件被写截断。
修法不是再赌一次，是拆。

### 5. 观察者开始互相复读
Quinn 和 Devon 同一天发两条“都正常”，第二条很快会变成背景噪音。
