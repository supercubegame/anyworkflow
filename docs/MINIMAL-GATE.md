# Minimal Gate

## 这条闸门为什么存在
`verify.py` 不是这份离线备份仓的最终闸门，它是**最小诚实闸门**。

它守的不是“这套工作流已经完整恢复”，而是更基础的一件事：

> 这份备份仓自己有没有在安静地说谎。

换句话说，它先防最蠢、也最容易悄悄发生的坏，再把更大的真值交给别的证据链。

---

## 它现在守哪 18 件事

### 1. `AGENTS.md` 与 `CLAUDE.md` 必须逐字相同
这守的是：同一套规则别长出两份各自漂开的文本。

### 2. `docs/RECOVERY.md` 必须存在
这守的是：别把“以后该怎么恢复”只留在脑子里。

### 3. `docs/BLIND-SPOTS.md` 必须存在
这守的是：不要让一份绿报告看起来像“什么都备了、什么都证明了”。

### 4. `manifest.json` 顶层键必须齐全
这守的是：别在一次整文件重写里悄悄把关键字段抹掉。

### 5. `not_backed_up` 不许是空数组
这守的是最值钱的一条：

> 盲区清单被清空，备份看起来更完整，而仓库一句话都不说。

这也是为什么 `VERIFY-EVIDENCE-0002` 故意拿它来做负向证明。

### 6. 回写 marker：workflow 与 manifest 逐字相同
真源是 `manifest.json` 的 `writeback.marker`，`scripts/attest_delivery.py` 从那里读它要找的标记，而 `.github/workflows/verify.yml` 把同一个值传给共享回写 workflow。

这两处漂开的话，症状是最难看的那种：**回写正常贴出评论，attest 却找不到它**，于是一条健康的链会被判成“结论没送达”，而修的人会去动 attest。

只改一处、删掉那一行、或者把 workflow 整体注释掉，三个变异体都判红。

### 7. composer 哨兵：写入方与核对方逐字相同
`scripts/compose-report.mjs` 往评论里写一个哨兵，`scripts/attest_delivery.py` 回头找它。

它承重的理由不明显，值得写清楚：共享回写 workflow 的**兜底评论带着同一个 marker**。也就是说“找到了带 marker 的评论”这句话**证明不了报告是完整的**。区分“完整报告”和“没有逐项证据的兜底”，全靠这个哨兵。

这条断言自己**不持有那个字面量**，它从两个真取用点各抄一次再比。整段重写弄丢一处，另一处还在用它，当场红。

### 8-11. 真抄本的四条

**先说它之前多糟：** `agents/*.md` 与 `vendor/ci-workflows/report.yml` 完全在闸门视野之外 —— 没有哈希、没有锚点、没有期限。**三份真抄本整个删掉都不会红**，而它们正是这仓的立仓之本。

备份类需求里最值钱的一句话是：

> 一份空壳备份和一份完整备份，在文件树上长得一模一样。

所以这四条**一条都不断言「文件存在」** —— git 已经证明了，那是空断言。

- **清单双向**：`REGISTERED_DIRS` 加上 `agents` 与 `vendor/ci-workflows`，目录里实际存在的集合必须等于登记集合。新增默认不通过。
- **逐字节身份**：三份抄本的 blob 哈希进登记表。
- **正文锚点**：每份登记多条承重的 token，逐条命中。它守的是哈希守不住的那一刻：一次正当重导出会让哈希变，而如果那次「重导出」其实是一份被抽空的壳子，重算登记值后闸门照样全绿。
- **恢复充分性**：「恢复这个 agent 需要哪几节」逐个断言非空。它报的是哪一节空了，不是笼统地说「不完整」 —— 「本来就空」和「导出丢了」要分得清。
- **新鲜度**：读回时间戳 + 30 天期限。它不证明此刻一致，它证明「30 天以内有人真的去核对过一次并写下了结论」。**两侧都能红**：过期红，而拿一个未来时间戳把期限涂绿也红。

**锚点故意选结构性 token（cron、字段名、文件路径、API 方法名），不选中文句子。** 理由写在 `manifest._tested_limits` 里：我逐字转写长中文会漂，而一个漂掉的锚点是假红工厂。

**锚点失配时更新锚点，绝不删锚点** —— 删掉是把承重断言改成装饰。

### 12-13. 跨抄本一致性，以及形近错字黑名单

这两条都不在计划里，都是做上面那四条时撞出来的。

**跨抄本一致性**：两份抄本各自都是忠实的读回，而它们互相矛盾 —— **这种形状没有任何单份断言看得见，因为每一份自己都是对的**。它上线就抳到了一个真问题：一个每天读回另一个观察者定时的巡检，手里的期望值已经不是那个定时了。

修不在本仓（要改 live prompt），所以登记成**带期限的义务**，而它三侧都红：不一致而没登记义务红、义务过期红、**做完了还挂着也红**。完成判据读两份真文件，不读我的报告 —— 一条靠自己声明完成的义务等于没有义务。

**形近错字黑名单（负向扫描）**：有一类字节漂移反复发生，而根因后来彻底定位了，**不在任何存储通道上，在我自己**：往文件里写中文时会敲成形近字，手写 Unicode 转义时会敲错码位（差一位），而两种都**字节长度不变**。

最贵的一处：一份讲「别安静地说谎」的文档，那两个字被换成了形近字，**一句话当场失去意义，而没有任何东西会喊**。

黑名单用码位构造（手写正是病因），并带一条自证：错字等于正字就红，因为一个拼错的黑名单项永远不会命中。**而黑名单对新错字默认泄漏** —— 实测两个漏网的例子，这一条已登记进 `_tested_limits`，不假装它守住了所有形近字。

扫描器**先剥注释再找**，并自证剥完还剩三成以上 —— 否则一份**记录**了错字的文件会被自己判红。这是同一个自指回环的第三次，前两次是 marker 印进报告、attest 日志印进评论。

### 14. 检查总数的等号，以及本文那个数

下限型的计数会自己漂（「最少 N 条」是个地板），所以登记值是等号。

**而本文开头那句「守哪 18 件事」是手写散文，它上一版就已经漂了** —— 写着七件事，而闸门早就不是七条。所以给它配了一条交叉核对：真值就在同一个仓里，所以这条做得成。

**逐条小节标题只到 15，而总数是 18。** 差的三条是上面合写的那几组里的（真抄本四条里的清单双向与逐字节身份各算一条，跨抄本与黑名单那段里又合写了两条，而共享回写消费者生成物挂在 invariants 那一节里）。**这句话本身就是一个提醒：散文里的结构永远追不上代码，能钉的只有那个数。**

### 15. `manifest.invariants` 与实际检查集合相等

**先说它之前多糟：**`invariants` 那几个键**从来没被读过**。它们看起来像一份「本仓守住了哪些不变式」的声明，而实际上是纯装饰：写什么都行，写错也行，删光也行。

上面那条总数等号只数个数，**它看不见「是哪几条」** —— 删一条、加一条，总数不变就不会红。所以这里比的是**集合**，两侧都红：新加一条检查而忘了登记红，删了一条检查而键还挂着也红。

**键用的是 id，不是标题。** 拿可读名字当键的话，「改个名」会变成承重操作 —— 而重命名应该是响亮的，不是静默的。

**它第一版写错了，而错法值得记下来：**最初它拿的是运行时那个 `checks` 列表，于是**排在它之后的检查它根本看不见**（还没 append 进去）。一条看不见部分目标的断言，对那一部分而言就是空的，**而它的覆盖面静静地取决于代码顺序**。现在改成扫源码里的 `check('<id>'` 真取用点，不依赖执行顺序，并带两条自证：扫到 0 个 id 就红，扫不到本条自己也红。

**顺带暴露了另一个手写偏移量：**上面那条计数断言用 `len(checks) + 1`，而那个 `+1` 假设自己排在最后。新增本条时它被插到了前面，于是计数算 16 而实际跑了 17。**修法不是把 `+1` 改成 `+2`**（那下次还会漂），而是把计数那一条真排到最后，并加一条自证守着它确实在最后。

## 它故意不守什么

### 不守 1：抄本此刻是不是等于真身
上面那四条只能证明抄本没被改过字、没被抽空、读回不超 30 天。**它们一条都不证明抄本等于真身** —— 那件事只能从仓外读回，而新鲜度那条守的就是「有人 30 天内真的去读过一次」。

### 不守 2：仓外真值是不是已经变了
例如：
- shared workflow 的远端主干现在是不是还长这样
- ClickUp 里的 live prompt 是不是已经变了
- 其它仓库里的 cross-repo 真值是不是还一致

这些值不在本仓库里，硬塞进最小闸门只会制造假确定性。

### 不守 3：skill summary 自动触发
必须靠冷启动对话实验来证明，不可能从这份仓内部直接判。目前最接近的证据是 `SUMMARY-TRIGGER-EVIDENCE-0001`，那是**行为证据**（正负样本各一个），不是内部归因。

### 不守 4：UI-only 字段
agent 工具显示名、某些 ClickUp 面板字段、workspace knowledge 的界面状态，这些都不在当前可读的抄本里。

### 不守 5：结论有没有送出去
这一条以前不在这个列表里，因为这仓压根没有回写。现在有了，而它**仍然不是 `verify.py` 的活**。

`verify.py` 是离线的、零网络的。“那条评论真的贴出来了吗”只能从仓外看，所以它由一个独立的 job 负责（见下一节）。把它塞进最小闸门只会让最小闸门开始假装能证明仓外的东西。

## 它上面还有两层

最小闸门只是第一层。三层合起来才是这仓一直在示范、而自己长期只有第一层的那套东西：

### 第二层：回写
共享 workflow（`ci-workflows/report.yml@main`）把逐项结果合成一条评论，贴到 PR 或 commit 上。

理由是本仓的 Actions 运行日志读不到，闸门红了之后手上只有一个比特：过 / 不过。二分推送去猜是哪一行错了，每一次猜都是一次“读着判断”。

### 第三层：送达核对（attest）
`scripts/attest_delivery.py` 回头去 API 上确认**这一次**那条评论真的存在。

它不是第二层的复读。回写那一步内部有“发完读回来”，但那是**监控自证清白**。attest 从外面看，看的和读评论的人拿到的是同一份东西。四个关键设计：

- **两条通道都查**：只查一条，另一条坏掉时它会安静通过
- **钉在本次运行上**：正文必须同时含本次短 SHA 和本次 run id。“存在一条带 marker 的评论”是幂等写入的经典假绿：上一次运行留下的那条会让它在回写完全坏掉的情况下照样通过
- **轮询别睡一觉**：判据是布尔，不是计数
- **自证**：同一个查找器在一个必然不存在的标记上必须返回 0 条；另有一批合成样本的离线用例每次先跑（样本数由那张表算，不手写），好的必须绿、坏的必须各自红

它 `exit 2` 的意思是“本次什么都没核对到”（自证没过，或前置条件缺）。**那不是绿**，而且和 `exit 1`（送达链有问题）是两件不同的事。

#### 实测记录

三条都已经拿到，详见 `VERIFY-EVIDENCE-0003`：

- **commit 评论通道**（run 32905110223）与 **PR 评论通道**（run 32907123136）各自绿过一次。一次运行只可能走到一条路，所以这两条必须分两次验。
- **闸门红的那次报告照样送达**（run 32908614769：闸门 failure、回写 failure、attest success）。
- **attest 自己真红过一次**（run 32911142277）。改歪一个 marker 之后，回写照样贴出了评论，而 attest 找到的是上一轮那条写着“全部通过”的陈旧评论。**它没有信** —— 因为正文里没有本次的 SHA 和 run id。

## 为什么故意只守这么少
因为这条闸门的任务不是“证明一切都对”，而是**先拦住最低级、最会安静发生的坏**。

如果一上来就把所有真值都塞进去，会得到两种坏结果：
1. 它开始假装能证明仓外的东西
2. 它自己变复杂，最后也需要另一条闸门来守它

这份仓库已经见过这种病了：一个 72KB 文件为了多守几件事，最后开始把自己写坏。

## 它和其它证据链的关系

### `VERIFY-EVIDENCE-0001`
证明：真输入会绿。

### `VERIFY-EVIDENCE-0002`
证明：坏输入会红，而且红在该红的地方。

### `VERIFY-EVIDENCE-0003`
证明：结论真的送达了（两条通道），闸门红的那次也送达了，而 attest 自己也会红。

### `verify.py`
证明：每次推送时，这 18 条最小诚实约束会被重新检查，而不是只在文档里写着。

四者合在一起，才是“这套东西不是摆设”。

---

## 什么时候该升级它
只有在出现下面这两种情况之一时，才值得加新检查：

1. **同一种静默坏法被真实踩过两次。**
2. **某个盲区已经被稳定地转成仓内可读证据。**

**而已经有好几条走的是第三种，值得写明白免得被当成先例：那几组耦合参数、以及形近错字那一条，都是改动自己造出来的**，新增的可验证行为要顺手补一条断言，否则等于一边修洞一边挖洞。

除此之外，不要为了“看起来更完整”往里塞新规则。那样最容易把最小闸门养成下一份会说谎的大文件。

---

## 一句话总结

> `verify.py` 守的不是“这套系统全对”，而是“这份离线备份仓至少别先对自己撒谎”，而“它的结论有没有送出去”，由它上面那两层负责。
