# Minimal Gate

## 这条闸门为什么存在
`verify.py` 不是这份离线备份仓的最终闸门，它是**最小诚实闸门**。

它守的不是“这套工作流已经完整恢复”，而是更基础的一件事：

> 这份备份仓自己有没有在安静地说谁。

换句话说，它先防最蠢、也最容易悄悄发生的坏，再把更大的真值交给别的证据链。

---

## 它现在守哪七件事

### 1. `AGENTS.md` 与 `CLAUDE.md` 必须逐字相同
这守的是：同一套规则别长出两份各自漂开的文本。

### 2. `docs/RECOVERY.md` 必须存在
这守的是：别把“以后该怎么恢复”只留在脑子里。

### 3. `docs/BLIND-SPOTS.md` 必须存在
这守的是：不要让一份绿报告看起来像“什么都备了、什么都证明了”。

### 4. `manifest.json` 顶层键必须齐全
这守的是：别在一次整文件重写里悄悄把关键字段抹掉。

### 5. `not_backed_up` 不许是空数组
这守的是最值钱的一条：

> 盲区清单被清空，备份看起来更完整，而仓库一句话都不说。

这也是为什么 `VERIFY-EVIDENCE-0002` 故意拿它来做负向证明。

### 6. 回写 marker：workflow 与 manifest 逐字相同
真源是 `manifest.json` 的 `writeback.marker`,`scripts/attest_delivery.py` 从那里读它要找的标记，而 `.github/workflows/verify.yml` 把同一个值传给共享回写 workflow。

这两处漂开的话，症状是最难看的那种：**回写正常贴出评论，attest 却找不到它**,于是一条健康的链会被判成“结论没送达”，而修的人会去动 attest。

只改一处、删掉那一行、或者把 workflow 整体注释掉，三个变异体都判红。

### 7. composer 哨兵：写入方与核对方逐字相同
`scripts/compose-report.mjs` 往评论里写一个哨兵，`scripts/attest_delivery.py` 回头找它。

它承重的理由不明显，值得写清楚：共享回写 workflow 的**兜底评论带着同一个 marker**。也就是说“找到了带 marker 的评论”这句话**证明不了报告是完整的**。区分“完整报告”和“没有逐项证据的兜底”，全靠这个哨兵。两侧漂开会让 attest 把每一次完整报告都判成说不清,或者更糟：把兜底读成完整。

这条断言自己**不持有那个字面量**，它从两个真取用点各抄一次再比。整段重写弄丢一处，另一处还在用它，当场红。

---

## 它故意不守什么

### 不守 1：真拄本是不是最新
这件事不是 `verify.py` 的职责。它只能看文件在不在，**看不出文件是不是昨天刚从真身读回的**。这部分由 `LIVE-READBACK-LEDGER.md` 和仓外时间戳负责。

### 不守 2：仓外真值是不是已经变了
例如：
- shared workflow 的远端主干现在是不是还长这样
- ClickUp 里的 live prompt 是不是已经变了
- 其它仓库里的 cross-repo 真值是不是还一致

这些值不在本仓库里，硬塞进最小闸门只会制造假确定性。

### 不守 3：skill summary 自动触发
必须靠冷启动对话实验来证明，不可能从这份仓内部直接判。目前最接近的证据是 `SUMMARY-TRIGGER-EVIDENCE-0001`,那是**行为证据**（正负样本各一个），不是内部归因。

### 不守 4：UI-only 字段
agent 工具显示名、某些 ClickUp 面板字段、workspace knowledge 的界面状态，这些都不在当前可读的拄本里。

### 不守 5：结论有没有送出去
这一条以前不在这个列表里，因为这仓压根没有回写。现在有了,而它**仍然不是 `verify.py` 的活**。

`verify.py` 是离线的、零网络的。“那条评论真的贴出来了吗”只能从仓外看，所以它由一个独立的 job 负责（见下一节）。把它塞进最小闸门只会让最小闸门开始假装能证明仓外的东西。

### 不守 6：真拄本还是不是真拄本
`agents/*.md` 和 `vendor/ci-workflows/report.yml` 目前**在这条闸门的视野之外**,没有 blob 哈希、没有正文锚点、没有新鲜度期限。它们可以被清成空壳而这条闸门全绿。

这是一笔明写的欠账，不是设计。修法是“备份类需求”那四条：清单双向、正文锚点、恢复充分性、新鲜度。

---

## 它上面还有两层

最小闸门只是第一层。三层合起来才是这仓一直在示范、而自己长期只有第一层的那套东西：

### 第二层：回写
共享 workflow（`ci-workflows/report.yml@main`）把逐项结果合成一条评论，贴到 PR 或 commit 上。

理由是本仓的 Actions 运行日志读不到,闸门红了之后手上只有一个比特：过 / 不过。二分推送去猜是哪一行错了，每一次猜都是一次“读着判断”。

### 第三层：送达核对（attest）
`scripts/attest_delivery.py` 回头去 API 上确认**这一次**那条评论真的存在。

它不是第二层的复读。回写那一步内部有“发完读回”，但那是**监控自证清白**。attest 从外面看，看的和读评论的人拿到的是同一份东西。四个关键设计：

- **两条通道都查**,只查一条，另一条坏掉时它会安静通过
- **钉在本次运行上**,正文必须同时含本次短 SHA 和本次 run id。“存在一条带 marker 的评论”是幂等写入的经典假绿：上一次运行留下的那条会让它在回写完全坏掉的情况下照样通过
- **轮询别睡一觉**,判据是布尔，不是计数
- **自证**,同一个查找器在一个必然不存在的标记上必须返回 0 条；另有九个合成样本的离线用例每次先跑，好的必须绿、坏的必须各自红

它 `exit 2` 的意思是“本次什么都没核对到”（自证没过，或前置条件缺）。**那不是绿**，而且和 `exit 1`（送达链有问题）是两件不同的事。

---

## 为什么故意只守这么少
因为这条闸门的任务不是“证明一切都对”，而是**先拦住最低级、最会安静发生的坏**。

如果一上来就把所有真值都塞进去，会得到两种坏结果：
1. 它开始假装能证明仓外的东西
2. 它自己变复杂，最后也需要另一条闸门来守它

这份仓库已经见过这种病了：一个 72KB 文件为了多守几件事，最后开始把自己写坏。

---

## 它和另外两条证据链的关系

### `VERIFY-EVIDENCE-0001`
证明：真输入会绿。

### `VERIFY-EVIDENCE-0002`
证明：坏输入会红，而且红在该红的地方。

### `verify.py`
证明：每次推送时，这七条最小诚实约束会被重新检查，而不是只在文档里写着。

三者合在一起，才是“这条最小闸门不是摆设”。

---

## 什么时候该升级它
只有在出现下面这两种情况之一时，才值得加新检查：

1. **同一种静默坏法被真实踩过两次。**
2. **某个盲区已经被稳定地转成仓内可读证据。**

第 6、7 条走的是第三种，值得写明白免得被当成先例：**那两组耦合参数是接回写这件事自己造出来的**,新增的可验证行为要顺手补一条断言，否则等于一边修洞一边挖洞。

除此之外，不要为了“看起来更完整”往里塞新规则。那样最容易把最小闸门养成下一份会说谁的大文件。

---

## 一句话总结

> `verify.py` 守的不是“这套系统全对”，而是“这份离线备份仓至少别先对自己撒谁”,而“它的结论有没有送出去”，由它上面那两层负责。
