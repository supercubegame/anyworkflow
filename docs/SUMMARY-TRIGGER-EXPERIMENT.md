# Summary Trigger Experiment

## 目标
证明的不是“结果像不像 skill 生效了”，而是：

> 这次对话到底是不是因为 skill summary 被自动加载，才走进了这套方法。

这和“模型自己已经学会了”不是一回事。

---

## 为什么这件事单独做
只看一个成功案例，最多只能得到：
- 结果很像 skill 生效了

得不到：
- 到底是 skill 触发了
- 还是模型自己学会了
- 甚至两个一起发生了

所以这件事不能拿平时的自然对话顺手猜，必须单独设计实验。

---

## 实验设计原则

### 1. 不复述技能摘要原句
不要在提示词里主动写：
- 先搭验证闸门
- 返回退出码
- PR 评论回写
- attest
- 先闸门后功能

否则你测到的只会是“模型顺着你的话继续写”。

### 2. 同时做正样本和反样本
只做正样本没有用。你会看到一个像成功的结果，但不知道边界。

必须同时回答：
- 该触发的时候会不会触发
- 不该触发的时候会不会乱触发

### 3. 记录看的不是结果质量，而是方法学迹象
重点不在“最终做得好不好”，而在这些迹象有没有出现：
- 先问项目类型 / 判据
- 先搭 gate，再写功能
- 主动提回写 / attest / blind spots / heartbeat
- 反样本里不应该凭空带出这一整套方法

---

## 正样本

### Prompt A
> 做个 2D 小游戏，自己把质量关好，我不想手动帮你验。

### Prompt B
> 做个简单网页工具，功能别花哨，但交付要自己验干净。

### 预期
如果触发成功，至少应该出现其中 3 条：
- 问项目类型
- 问“跑起来”的判据
- 先做 gate / verify 入口
- 主动把回写链条说出来
- 把手动设置一次说全

---

## 反样本

### Prompt C
> 帮我改写这段 README 文案，让它更像热门开发工具仓库首页。

### Prompt D
> 给我总结一下这套工作流最值钱的 3 条经验。

### 预期
如果边界是对的，这类对话**不该**自动带出：
- gate-first 实施步骤
- PR / commit 评论回写
- attest
- heartbeat
- “先搭验证闸门再写功能”整套流程

如果它对反样本也自动带出整套方法论，那说明 summary 太宽，或者模型已经内化过头，归因不干净。

---

## 记录模板

每次实验至少记这四件：
- 使用的 prompt
- 是否点名加载过 skill（必须是：没有）
- 出现了哪些方法学迹象
- 结论：更像 skill 触发 / 更像模型自己会了 / 无法定案

---

## 结论分级

### A. 该触发时触发，不该触发时不触发
这是最强结果。可以说 summary 自动触发**有硬证据**了。

### B. 正样本像通过，反样本也带出同样方法
说明方法论可能已经被模型内化，**不能把功劳算给 summary**。

### C. 正样本也不带出这套方法
说明 summary 触发这半边还没站住。

---

## 这份实验文档在守什么
它守的不是工作流能不能跑，而是**归因别写错**。

因为最危险的错法不是失败，而是：

> 一次结果看起来很像 skill 被成功加载了，于是就把“模型自己会了”误记成“机制已验证”。

这正是这份实验存在的理由。
